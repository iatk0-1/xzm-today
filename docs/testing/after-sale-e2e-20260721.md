## 已确认缺陷

### AFS-001：用户撤销售后后无法重新申请

- 严重级别：P1
- 售后 ID：`337777930237120512`
- 前置状态：售后 `pending`
- 操作：用户撤销售后，再对相同订单项重新申请。
- 预期：撤销释放订单项，允许重新申请。
- 实际：重新申请返回 HTTP 400，提示该商品已有进行中的售后。
- 原因定位：`AfterSaleService.apply()` 的防重复逻辑只放行 `rejected`、`refunded`，未放行 `cancelled`。

### AFS-002：仓库验收失败后仍可退款

- 严重级别：P1（资金风险）
- 售后 ID：`337778792955121664`
- 操作链：退货退款审核通过 → 用户寄回 → 管理端选择“验收不通过” → 管理端退款。
- 预期：验收失败时退款接口必须拒绝，售后保留待人工处理状态。
- 实际：退款成功；售后与明细均变为 `refunded`，订单变为 `cancelled`。
- 日志证据：`receive_fail` 后紧接 `refund`。
- 原因定位：新版明细退款分支仅检查明细状态 `received`，未检查主单 `warehouse_check=pass`。

### AFS-003：混合售后收货后主单错误保持 approved

- 严重级别：P1
- 售后 ID：`337785020481540096`
- 订单 ID：`337776022122401792`
- 场景：部分发货订单同时包含：
  - 未发 1 件：`refund`，已自动退款；
  - 已发 1 件：`return_refund`，仓库验收通过。
- 预期：退货明细收货后，主单应进入可继续退款的明确状态（如 `received`），管理端显示“确认退款”。
- 实际：
  - `refund` 明细：`refunded`
  - `return_refund` 明细：`received`
  - 主单：仍为 `approved`
- 影响：管理端按 `approved` 继续渲染“仓库收货”，无法正常展示“确认退款”；重复收货还可能重复执行库存入库。
- 原因定位：`updateMainStatus()` 未覆盖 `refunded + received` 的混合状态组合，落入默认 `approved`。

### AFS-004：混合售后第一次部分退款写入主单级退款 ID，阻断剩余明细退款

- 严重级别：P1（资金与状态一致性风险）
- 售后 ID：`337785020481540096`
- 操作链：审核混合售后时，未发货 `refund` 明细先自动退款。
- 实际：主单立即写入 `wechat_refund_id=e2e_after_sale_337785020481540096`；之后已发货 `return_refund` 明细收货完成，再调用退款接口时命中主单级幂等判断并提前返回。
- 最终状态：
  - 主单：`approved`
  - 退货明细：`received`
  - 仅退款明细：`refunded`
  - 订单：`shipped`
- 预期：幂等与退款交易应按可退款批次/明细管理，第二阶段退款可以继续执行，最终主单与全部明细进入 `refunded`。
- 原因定位：`AfterSaleService.refund()` 在入口按主单 `wechatRefundId` 全局幂等，无法支持混合售后的分阶段退款。

- 测试 SKU 为无限库存，无法通过库存余额验证入库数量；已通过售后日志和状态验证相关调用路径。

## 后续统一修复建议（本轮未执行）

1. 防重复校验放行 `cancelled` 售后，并按历史退款数量限制剩余可售后数量。
2. 所有 `return_refund` 退款路径统一强制校验 `warehouse_check=pass`。
3. 重写混合明细的主单状态聚合规则，显式覆盖 `refunded + received`、`refunded + approved` 等组合。
4. 将退款幂等从主单级改为退款批次/明细级；一个售后单允许多阶段、多个退款交易号。
5. 给仓库收货接口增加明细幂等保护，防止重复 `refund_in`。
6. 为上述四个缺陷补后端集成测试和小程序 E2E 回归用例后再修复。
